Browserpod document
BrowserPod: Development environments in your browser[a]
Run Node.js projects in your browser, unmodified (Python, Ruby, and more coming in the future).[b]


Access the local http server in the same page or from another tab to view, test, and iterate; or share it with others, thanks to Portals.


See it in action in our SvelteKit+Vite demo: https://vitedemo.browserpod.io/
What can it do
Project showcase
Run a demo of your project directly in the user's browser, without any explicit setup or installation, and secured by the browser's sandbox.
Interactive documentation / tutorials
Enrich your documentation and tutorials with interactive components, without the need for any server-side infrastructure.
AI Agents environment
Let AI assistants and Agents run loose on your project, but isolated from the rest of your system.
How to use it
BrowserPod has a simple yet powerful API.


You can get up an running with few simple steps.


First, you need to boot your pod:


const pod = await BrowserPod.boot({ apiKey:"...", nodeVersion:"22", /*...*/});
	

Then, you need to add your project's files to the pod. Currently, you need to fetch the contents yourself, and re-create the directory structure inside the pod's filesystem. We will add more convenient setup methods in the future:






await pod.createDirectory("/project");
for await (const f of myfiles) {
 const response = await fetch(f.url);
 const buffer = await response.arrayBuffer();
 const fd = await pod.createFile(f.path);
 fd.write(buffer);
 fd.close();
}
	



Then, run any setup step required to initialize your project:


await pod.run("npm", ["install"], { cwd: "/project" });
	

And finally, run the dev server (or whatever workload your project provides):
await pod.run("npm", ["run", "dev"], { cwd: "/project" });
	

Listening ports are associated with a Portal, which you can embed in the page with an IFrame, or visit from another Tab, or even another device, anywhere in the World.
To get notified when a portal is created, do:


pod.onPortal(({url, port} => { /*...load iframe...*/ });
	How does it work
BrowserPod is built on top of CheerpOS, an Operating System interface that provides the Linux syscall interface to Wasm programs running in the Browser.


BrowserPod ships with a build of Node.js that targets CheerpOS.


Instead of using an embedded V8 engine to run JavaScript, the Browser's engine is used instead.


This allows BrowserPod to run your JavaScript code at native speed.


Everything else (Node's builtin JS modules, libuv, and Node's internal C++ code) stays the same, to guarantee maximum compatibility.


Multiple versions of Node will be supported, and we plan to support new LTS versions in a timely manner.


Using the same foundation, we plan to support other languages and frameworks, like Python and Ruby (including Ruby on Rails).

Q: What are the differences between BrowserPod and WebContainers?
A: Both BrowserPod and WebContainers are technologies that enable running Node.js code in the Browser.


WebContainers also supports running WASI applications, and ships a build of `python`, and a handful of utility programs like `jq`.
BrowserPod, while initially focusing on Node.js, will soon add support support for Python and Ruby, and we plan to include useful program like git and curl.


While the general architecture of the two product is similar, BrowserPod has a secret weapon: CheerpOS.
Like WASI, CheerpOS is a system interface that applications can target, but unlike WASI its goal is to provide the full Linux kernel APIs, and allow as much code as possible to compile for the Web without modifications.


BrowserPod allows a local web server to be accessed from different tabs on the same browser without the need to change Browser settings. The server can actually be accessed from anywhere in the World by sharing its Portal URL.


Another important difference is the licensing and pricing models.[e] For example there is no restriction on the usage of BrowserPod as part of AI products.


Q: What is a Portal?[f]
A: All listening HTTP sockets inside a Pod are associated with a Portal: a unique subdomain of browserpod.io that allows anyone to connect to the server from the Internet.
Clodflare Workers are used to proxy the traffic and serve it over HTTPS to the Internet.

Notes
Webcontainers vs Stackblitz. We are making Webcontainers. our customers make the equivalent Stackblitz.


This means that we are not concerned with the details of accessing github private repos. We will nonetheless add a tutorial/guide/faq about ways to do it (put ssh key or netrc file in the fs)


This also means that our customers are going to expose their API keys to users. We need to think about this. The Webcontainers dashboard has a whitelist of allowed origins. localhost always allowed without any kind of auth (actually ONLY allowed without auth).
We don't like the idea of having no auth on localhost, but this makes the API key leak issue more complex to handle.


Webcontainers's filesystem seems quite simplistic and basic: just a json blob (or a binary post-processed version:a "snapshot") that you declare in your js (🤮). Also persistence is opt-in and manual (supposedly you can restore a "snapshot"? need to try it)
Svelte and maybe others are integrated with this system though and the node deps are pre-packaged to speed things up.
Also the node deps files are cached by the browser's http cache at least.
They officially recommend to include the lock file in the fs to speed things up.


We want to offer a snapshot feature of some kind ourselves.


On Webcontainers you can only call boot() once at the start. this is the thing that is billed. All processes share the same instance. You mount the fs on the instance.
Any use for multiple BrowserPod instances? unclear.


We want to compile git for downloading repos. if that does not work, tar+unzip should do at least for github.


For the dashboard we want to be quite similar to Webcontainers, but we want to show the EULA when creating a free api key.
All the keys are tied to the account plan and are tied to a global metering system.
